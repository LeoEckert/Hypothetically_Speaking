# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An agent that takes a plain-English ageing/longevity research question and autonomously plans, retrieves evidence, calls biological data tools, runs a real in-silico gene/pathway enrichment analysis, and returns a cited, defensible markdown report. Built for the "Build a Longevity AI Scientist" hackathon challenge.

There is no platform-held LLM key at all: every visitor brings their own, either a free OpenRouter key (no credit card — openrouter.ai/keys) or their own Anthropic key, guided by a required first-run onboarding popup (`frontend/src/components/OnboardingDialog.tsx`). This isn't a soft fallback — `GET /api/run` genuinely cannot do anything without one, by design: a platform-held key for either provider would be a shared resource a handful of concurrent visitors could exhaust (verified: OpenRouter's free tier is 50 requests/day *per account*, worse to share across every visitor than to hand out individually). Every run budget is sized to fit inside a hard 300-second-per-run ceiling (Vercel Fluid Compute's limit — see `backend/agent/loop.py`'s `REPORT_RESERVE_SECONDS`/`MAX_RUN_SECONDS`). Deployed as **one Vercel project** serving both the static frontend build and the backend as a Python serverless function (`api/[...path].py`) — see `docs/DEPLOY.md` for the full setup, including a real Vercel-account-specific gotcha (native ASGI/FastAPI support is broken there; the backend bridges through `a2wsgi`'s WSGI adapter instead) worth reading before assuming a fresh deploy will just work. **Known unresolved bug**: multi-segment `/api/*` routes (`/api/run/<id>/evaluate`, `/api/admin/*`, `PUT /api/tools/<name>`) 404 at the platform level in production — the catch-all filename only matches a single path segment on this account; see `docs/DEPLOY.md`'s routing section before touching this again.

## Branching & workflow

As of 2026-09-15, this repo uses a `main`/`dev` split with real branch
protection (GitHub rulesets), not ad hoc pushes to `main`:

- **`main`** is the protected, production branch — it's what
  `.github/workflows/deploy-frontend.yml` deploys on every push, and it's
  what `docs/DEPLOY.md`/`CLAUDE.md` mean whenever they say "deploy = push to
  main". It **requires a pull request** now (no direct pushes, for anyone,
  including an agent session) and the CI workflow (`.github/workflows/ci.yml`
  — pytest + frontend build/lint, the exact commands in this file's Commands
  section) must pass before merging. Force-pushes and deletion are blocked.
- **`dev`** is the integration branch and GitHub's default branch (so a new
  PR/clone lands here by default). Direct pushes are still allowed here
  (deliberately — this is where day-to-day work happens), but **feature
  branches are the expected norm from here on**, not a suggestion: cut a
  branch off `dev` (`feature/<short-description>`, or the existing
  `claude/<description>` convention for agent-authored work), open a PR back
  into `dev` once it's ready. `dev` itself only has force-push/deletion
  blocked — no PR requirement, no required CI check. `dev` also deploys on
  every push, same as `main`, to its own stable URL
  (`hypothetically-speaking-dev.vercel.app`) — see `docs/DEPLOY.md`'s
  "Current live deployment" section for how that's wired up (a Preview
  deployment behind a custom alias, plus working around Vercel's default
  Preview SSO gate).
- **Shipping to production** means promoting `dev` → `main` via a PR once
  `dev` is in a state worth deploying — that PR is what actually triggers a
  Production deploy (`hypothetically-speaking.vercel.app`) once merged.

This replaced an earlier phase of this project where `main` was the single
working+deploy branch with no protection at all and several long-lived,
never-merged branches accumulated with no cleanup policy — all of that was
audited and cleaned up in the same session this workflow was introduced
(the branches genuinely worth keeping had already been merged via PR; the
rest were confirmed fully-merged-and-redundant or too stale to trust and
deleted).

## Architecture

```
frontend/            Vite + React + TS + shadcn/ui SPA — static build with no server code, shipped inside the same Vercel project as backend/
backend/agent/        the plan -> retrieve -> compute -> revise -> report loop (provider-agnostic tool-use, see backend/agent/providers/), plus cost/usage accounting
backend/tools/         one wrapper per external tool, each independently toggleable + mockable
backend/server/        FastAPI app: POST /api/run, SSE stream of trace events, tool toggle + config/tools endpoints
scripts/               run_demo.py (canonical run + saved transcript), validate_citations.py, fetch_datasets.py
docs/                  ARCHITECTURE.md (design + diagram), DEPLOY.md (Vercel/Nebius setup), DEMO_SCRIPT.md
vercel.json, .github/workflows/deploy-*.yml   deployment config (see docs/DEPLOY.md)
```

`frontend/` and `backend/` run as independent processes locally (two terminals: `uvicorn` + `vite dev` over `localhost`), but ship together in production as **one Vercel project** — the static frontend build plus the backend packaged as a Python serverless function serving `/api/*` (same-origin in prod; CORS config still matters for local dev pointed at a deployed backend — see `docs/DEPLOY.md`). See `docs/ARCHITECTURE.md`'s System diagram.

### The agent loop (`backend/agent/loop.py`)

A **manual**, provider-agnostic tool-use loop — deliberately not the Claude Agent SDK, so every step is inspectable state rather than framework magic. Every LLM call goes through `backend/agent/providers/`'s `get_provider(api_keys, tier)`, never a direct SDK client. Which provider a run gets (`providers/__init__.py`): only an OpenRouter key → `OpenRouterProvider` (free models); only an Anthropic key → `AnthropicProvider`; **both → `FallbackProvider`** (`providers/fallback.py`): the run starts on **Claude** and moves to OpenRouter's free models only if Claude actually fails (a 429 that survived the provider's own retries, a 402, a vanished model/404, 5xx, transport error, **or a completion carrying neither text nor tool calls** — a 400/401/403 propagates instead, since a bad key is just as bad on the fallback), sticky for the rest of the run. Claude leads because the free roster could not be trusted with the hardest generation in a run, the final report: those models routinely answered it with an empty completion or with the ```json hypotheses block alone, a quality failure no status code announces — hence the empty-completion rule. A switch only works because **each adapter rebuilds its native messages from `LLMResponse`'s provider-neutral fields (`text` + `tool_calls`), never from `raw`** — `raw` is one provider's private wire format, and feeding an OpenAI-shaped transcript to the Anthropic SDK produced a guaranteed 400 (see `tests/test_provider_interop.py`); `costs.py` prices each model bucket on its own terms and reports `fell_back_from`/`fallback_reason`. The Claude model per tier comes from **`backend/config/models.toml`** via `backend/agent/model_policy.py`, keyed by deployment (`APP_ENV`, else Vercel's `VERCEL_ENV`): production and local dev run the Sonnet/Haiku mix and honour a user's Settings pick (`api_keys["ANTHROPIC_MODEL"]`/`["GROUNDING_FAST_MODEL"]`) or the same-named env vars; the `dev` preview deployment pins both tiers to Haiku and ignores overrides (`allow_override = false`), so dev-branch testing on someone's Anthropic key never bills Sonnet. `GET /api/config` exposes that policy as `anthropic_models` for the frontend. Both providers send prompt-cache breakpoints: `AnthropicProvider` on the system prompt, tools and a rolling `tool_result`; `OpenRouterProvider` mirrors the first and third (system prompt, rolling tool result — `cache_control` is forwarded to Anthropic/Gemini-hosted models and ignored elsewhere, where the shared prefix is auto-cached) and reads `prompt_tokens_details.cached_tokens` back into `cache_read_input_tokens`. Caching is never allowed to break a run: a 400 on a request that carried content-part arrays is retried once with plain strings (`_call_with_retry`). `OpenRouterProvider.stream()` also collects `delta.reasoning` (used as the body only when no `content` arrived at all), accumulates tool-call deltas, and reports the real `finish_reason` — reading `delta.content` alone is what let a reasoning-only or truncated turn come back as a cheerful empty `end_turn`. Both are BYOK in production — `api_keys` from the request (see the frontend's required onboarding popup); the `os.environ` fallback in `get_provider()` is a local-dev convenience only (see that module's docstring), not a platform key real users ever rely on. `loop.py` builds a provider-agnostic `Transcript` (see `providers/base.py`) rather than raw Anthropic content-block dicts — each provider converts that to/from its own wire format inside `create()`/`stream()`. Phases:

1. **PLAN** — the model states its interpretation/assumptions, proposes 2-4 candidate hypotheses, and picks tools to check each against. Never blocks waiting for clarification.
2. **ACT** — standard tool-use loop: the model calls tools via the registry (using a run-start snapshot of enabled tools, see below), results are recorded as tool-result turns on the `Transcript` and simultaneously registered in the evidence registry under a stable citation ID (e.g. `[PMID:12345678]`, `[OT:ENSG00000142192]`, `[NCT:NCT01234567]`).
3. **COMPUTE** — once evidence names candidate genes/proteins, the agent calls `extract_genes` (Nebius-hosted NER over retrieved abstracts, or a regex heuristic fallback when no `NEBIUS_API_KEY` — platform or BYOK — is set) then `run_enrichment` (g:Profiler) — this is the one required "real computed result, not summarization" step.
4. **REVISE** — a dedicated forced turn: revise the hypothesis ranking against all evidence + the enrichment result, name contradicting evidence, name the next experiment.
5. **REPORT** — final markdown with fixed sections (Hypothesis / Evidence For / Evidence Against / Confidence & Uncertainty / Failure Modes / Next Experiment / Tool Trace); every factual sentence must end in a `[citation-id]` resolvable in the evidence registry.

Run budget is enforced by `RunState` (`backend/agent/state.py`): `MAX_TOOL_CALLS` (default 15, `HARD_MAX_TOOL_CALLS` 25 — raised from an initial 8/12 after real runs on thorough questions wanted more) and `MAX_RUN_SECONDS` (default 260, with a `REPORT_RESERVE_SECONDS` — 100s — held back so the unconditional REVISE+REPORT calls after the ACT loop still fit inside `max_run_seconds` rather than running past it). These are sized for a hard 300-second external platform ceiling (Vercel Fluid Compute) — scaled down from an earlier 30/40/1080s VM-era budget, pending empirical retuning against real timed runs (`scripts/run_demo.py`) once a real OpenRouter key's actual token/wall-clock profile is measured. On budget exhaustion the loop still forces the REPORT phase over whatever evidence exists, marking the run `partial` rather than truncating silently. `on_event(event: dict)` is threaded through the whole loop so callers (the FastAPI SSE endpoint, `scripts/run_demo.py`) can stream/record a run live without touching the loop internals.

A known, previously-reproduced bug (fixed): Claude occasionally returns a text content block with empty/whitespace-only text alongside a tool_use or thinking block; resending that verbatim on the next turn gets a 400 ("text content blocks must be non-empty") and aborted the whole run. This guard (`_strip_empty_text_blocks`) now lives inside `AnthropicProvider` itself (applied before any request is sent), not in `loop.py` — it's an Anthropic wire-format detail, not something the loop or the OpenRouter path need to know about.

Two failure modes get a specific, user-actionable message instead of the generic `## Run Error` catch-all: no LLM key at all (`NoProviderAvailable` — should only happen if the frontend's required onboarding popup was somehow bypassed) and a key rejected by its provider (`anthropic.AuthenticationError`/`PermissionDeniedError`, `openai.AuthenticationError`/`PermissionDeniedError` — covers both a missing and an invalid/exhausted key uniformly, so there's no need to pre-validate a key anywhere).

### Tool contract (`backend/tools/registry.py`)

Every module under `backend/tools/` exposes:
- `SPEC` — the Claude tool schema (name, description, input_schema)
- `run(args: dict) -> dict` — returns `{"summary": str, "items": [{"id", "url", "summary", "raw"}, ...], "mock": bool, "error": str | None}`, plus an optional extra `usage: {"prompt_tokens", "completion_tokens"}` key (currently only `extract_genes`, for Nebius cost accounting)

A tool must **never raise** out of `run()` for a missing key / network failure — it degrades to a mock result with the same shape (`registry.run_tool` also catches exceptions defensively as a second line of defense). This mock-fallback contract is what `tests/test_tools.py` checks for every tool.

`ENABLED_TOOLS` (comma-separated env var) sets the default — a **blank-but-set** value (confirmed to happen on Vercel) is treated the same as unset (everything enabled), not "nothing enabled"; same bug class as `loop.py`'s `_env_int()` and as the `ANTHROPIC_MODEL=""` that once reached the API as the model name (400 "model: String should have at least 1 character"). `backend/agent/env.py`'s `env_str()`/`env_int()` exist for exactly this — any env read with a default goes through them, never bare `os.environ.get(name, default)`. `registry.set_tool_enabled(name, bool)` — exposed via `PUT /api/tools/{name}` and driven by the frontend's per-tool switches — layers a runtime-only override on top (resets on process restart). `run_tool(name, args, enabled_names=..., api_keys=...)` takes an explicit set so a run's tool availability is **snapshotted once at run start** (`state.enabled_tools`) — toggling a tool mid-run never affects that in-flight run, only the next one.

**BYOK**: `registry.KEY_ENV_VAR` maps the three keyed tools (`tavily`→`TAVILY_API_KEY`, `amass`→`AMASS_API_KEY`, `extract_genes`→`NEBIUS_API_KEY`) to their env var. `registry.PAID_TOOLS` (`amass`, `extract_genes`) flags which keyed tools have no free tier at all — surfaced to the frontend as `GET /api/tools`'s `paid` field, which `ToolsPanel.tsx` renders as a "paid" badge and uses (alongside `key_configured`/a BYOK key) to disable that tool's switch until a key exists. `run_tool`'s `api_keys` param (from `RunRequest.api_keys`, i.e. the frontend Settings menu) injects a matching key into a reserved `args["_user_api_key"]` field rather than changing the `run(args: dict) -> dict` contract — each tool's own key lookup checks that field first, falling back to the platform env var, then to its mock/heuristic default. Never stored on `RunState` (which gets dumped into the persisted report JSON) — passed as a plain function parameter down the call graph and discarded after use.

### Cost/usage tracking (`backend/agent/costs.py`)

Every run accumulates real LLM token counts (against whichever provider it actually used), Nebius token counts, Amass account credit balance (sampled before/after via `amass_tool.get_credits()`, skipped entirely when no Amass key — platform or BYOK — exists), and Tavily/free-tool call counts, then `build_cost_summary(state, provider, api_keys)` turns that into a per-provider breakdown on the `done` SSE event and the saved report JSON. The LLM row (still keyed `"anthropic"` in the JSON for frontend/report compatibility) carries `provider` ("anthropic"/"openrouter"/`None`), `free_tier` (true and `usd: 0.0` for OpenRouter — a **known** rate, not an unpriced one), and `key_source` ("user"/"platform"/"unset" — "platform" here means the local-dev env var fallback, not a real platform-funded key). Rule for everything else: **never show a `$` figure without a configured rate** — Anthropic has a hardcoded (drifts, re-verify) price table; Nebius/Amass/Tavily need `NEBIUS_PRICE_PER_1M_INPUT`/`_OUTPUT`, `AMASS_PRICE_PER_CREDIT`, `TAVILY_USD_PER_CALL` set or their `usd` stays `null` with `rate_configured: false`; those three also carry `key_source` so a `$` figure is never misattributed to the platform when it was actually billed to a user's own key.

### Evidence registry & citation discipline (`backend/agent/state.py`)

`RunState.evidence` maps citation ID -> `EvidenceItem {id, source, url, summary, raw}`. The report prompt requires every claim to carry a matching `[id]`. `scripts/validate_citations.py` parses a saved run's report, extracts every `[id]` marker, and fails if resolved-citation coverage of factual sentences is below 95% or any marker doesn't resolve to a real registry entry.

### Backend API (`backend/server/app.py`)

`GET /api/config` (dev-mode demo question, `anthropic_key_configured`/`openrouter_key_configured`/`default_provider` — reporting only whatever a local-dev env var happens to hold; there's no platform key in production), `GET /api/models` (the live list of currently-free, tool-calling-capable OpenRouter models plus which one `get_provider()` would pick by default — backs the frontend's model picker in Settings, no key needed since OpenRouter's catalog is public), `GET /api/tools` / `PUT /api/tools/{name}` (roster + toggle + BYOK metadata: `key_env_var`, `key_configured`, `paid`), `POST /api/run` (runs the whole agent loop and streams its trace as SSE **within this one request/response** — no separate start/stream endpoints any more), `POST /api/run/{run_id}/evaluate` (takes the finished run's `report`/`hypotheses`/`evidence` in the request body, since there's no server-side run cache to look `run_id` up in). CORS via `ALLOWED_ORIGINS` (exact list) + `ALLOWED_ORIGIN_REGEX` (default matches any `*.vercel.app`, since Vercel preview deployments get a fresh hostname per branch).

This app now holds **no state that needs to survive between requests** — `POST /api/run` bridges its background worker thread's events onto an `asyncio.Queue` natively (via `loop.call_soon_threadsafe`) and streams them out as they arrive, closing on `stream_end`; cancelling a run means aborting that connection (checked via `request.is_disconnected()`), not a separate `/cancel` endpoint. This is deliberate, not just a simplification: it's what makes the backend deployable on stateless/serverless hosting (see `docs/DEPLOY.md`) instead of requiring a persistent VM — the old two-endpoint design (`POST /api/run` returns a `run_id`, a separate `GET .../stream` tails an in-memory per-run event list) depended on one long-lived process with shared memory across requests, which serverless doesn't give you.

### Frontend (`frontend/`)

Vite + React + TypeScript + shadcn/ui. `src/store/runsStore.ts` is a vanilla subscribe/getSnapshot store (via `useSyncExternalStore`) backing a `localStorage`-persisted run history — every SSE event for every run gets appended there live. `src/lib/runStream.ts`'s `startAndStream()` POSTs to `/api/run` and reads the streaming response body directly, parsing SSE `data: ` lines itself — it can't use the native `EventSource` API (GET-only, no request body) now that starting and streaming a run is one request; cancelling calls `cancelCurrentStream()`, which aborts that fetch. `src/store/apiKeysStore.ts` is the same vanilla-store pattern for BYOK keys (Anthropic/OpenRouter/Tavily/Amass/Nebius), in `localStorage` (unlike the admin token's `sessionStorage` — these are load-bearing for normal use, not an occasional elevated action; `hasUsableLlmKey()` is what actually gates whether a run can start). `components/OnboardingDialog.tsx` is a required first-run popup (guides a visitor to a free OpenRouter key or their own Anthropic key) — shown automatically whenever `hasUsableLlmKey()` is false and re-shown from `App.tsx`'s `handleRun()` if someone dismissed it and then tries to run anyway; `components/SettingsDialog.tsx` (a gear icon in `AppHeader`) is the same keys for managing them anytime, plus model pickers (`src/store/modelStore.ts`/`src/hooks/useModel.ts`, same vanilla-store pattern as `apiKeysStore.ts` but a separate store since none of it is a secret; `localStorage` key `hs_model_prefs_v2`, migrating the old single-value `hs_model_pref_v1`): an OpenRouter pick backed by `GET /api/models` — "Auto" or a specific free model — and a Claude main/fast pick, disabled with a note when `GET /api/config`'s `anthropic_models.allow_override` is false (the dev preview). Every set preference is merged into the request's `api_keys` as `OPENROUTER_MODEL`/`ANTHROPIC_MODEL`/`GROUNDING_FAST_MODEL` (`App.tsx`'s `apiKeysForRequest()`). `ReportView` renders a short explanation rather than an empty bordered card when the report has no sections — that blank card was the visible symptom of a `done` event carrying `report: ""`, and it also covers history entries saved before the backend guaranteed a body. `CostPanel` surfaces `fell_back_from`/`fallback_reason` and the cached-token count, so a mid-run provider switch and a dead cache are both visible. Key inputs save on the Save button *or* Enter, and closing the dialog commits any pasted-but-unsaved key (an emptied field is not treated as a clear — that stays the explicit Clear button), which is what fixed the "I pasted my key and it didn't save" report. Components: `Sidebar`/`HistoryList`/`ToolsPanel`/`HowItWorksPanel`/`SettingsDialog`/`OnboardingDialog`, `ComposeBox`, `TraceTimeline`/`ToolStepCard`/`ReasoningBlock`/`ErrorBanner`, `ReportView` (resolves `[citation-id]` markers against the `done` event's evidence map), `CostPanel` (also shows which model actually ran a finished run, via `cost.anthropic.model`), `EvaluationPanel` (side-by-side original-vs-revised diff of the AI evaluation — see below), `KnowledgeTrajectory` (the grounding's premise graph and activation path, drawn in the browser — see below).

**Knowledge trajectory view** (`KnowledgeTrajectory.tsx` + `lib/trajectory.ts`): the graph of what the grounding checked — question → premises (coloured by verdict) → entities, hypotheses aimed at the weak links, records behind a toggle — plus a stage-ordered "activation path" (L0 split, L1 links, one L2 verdict per link with its rationale, L4 kept/rejected). It is built entirely from events the run already streams and `runsStore` already persists: `inputFromSteps()` draws it live from the `grounding_step` events in `ProgressView` (links appear at L1 dashed as "checking…" and take their colour as each L2 verdict lands; hypotheses attach when the final event arrives), `inputFromGrounding()` draws the finished run in `ResultsView`. `buildGraph()`/`walk()`/`layout()` mirror `backend/kgviz/graph.py` (same node ids via `premise_id`/`concept_id`/`hypothesis_id`, same edge kinds and virtual `subject`/`object`/`tested_by` links, same sorted BFS/DFS) and were checked identical to it on the same fixture — so it needs no backend, which is what makes it work on the stateless deployment where `runs/knowledge.db` never persists. What it cannot show is cross-run: other runs of the same question and each link's verdict history (see Open TODOs).

**Evaluation diff view** (`EvaluationPanel.tsx` + `lib/evalDiff.ts`): the AI evaluation renders as a per-section diff rather than a wall of revised prose. `buildSectionPairs()` pairs each critique's section with the original report section of the same heading (backend `RUBRIC` keeps `title` and `report_heading` identical, so no hardcoded heading table is needed), flattens both to prose, and word-diffs them. The change ratio picks the presentation: under 2% the section is `unchanged` and collapses; over 60% it is `rewritten` and both versions render as clean markdown, because word-level highlighting on a wholesale rewrite marks nearly every word and reads as noise; in between it is `revised` and gets inline strikethrough/underline highlighting. Each section's change-log entry and critique findings render next to that section rather than in a footer. `?evalpreview` in `vite dev` renders the panel against a local, gitignored `frontend/public/eval-fixture.json` so the component can be iterated on without a full agent run.

### Tools wired into the loop

Free/keyless by default, no BYOK needed: `open_targets`, `pubmed` (E-utilities), `clinicaltrials` (ClinicalTrials.gov v2), `genage_drugage` (local HAGR CSVs fetched once via `fetch_datasets.py`), `run_enrichment` (g:Profiler).

Keyed, BYOK-able (platform key optional, falls back to mock/heuristic without one): `tavily` (web/paper/trial search — has a real free tier), `amass` (Amass Cores API — biomedcore/trialcore/drugcore/patentcore/genecore/regulatorycore, confirmed contract — no free tier), `extract_genes` (Nebius-hosted NER, regex-heuristic fallback without a key).

Note: the registry key and `ENABLED_TOOLS` name for the enrichment tool is `run_enrichment` (must match the tool's `SPEC["name"]`, which is what Claude actually calls) — the module file is still `backend/tools/enrichment_tool.py`. Keep the registry key and `SPEC["name"]` in sync for every tool, or the tool silently looks "disabled" whenever Claude calls it.

- **Empirical budget tuning**: `MAX_TOOL_CALLS`/`HARD_MAX_TOOL_CALLS`/`MAX_RUN_SECONDS`/`REPORT_RESERVE_SECONDS` (`backend/agent/loop.py`) and the grounding depth constants (`backend/grounding/adapters.py`) were scaled down from their 1080s-VM-era values by proportion, not measured — re-tune against real timed `scripts/run_demo.py` runs once a real OpenRouter key's token/wall-clock profile is known (the ACT loop resends the whole growing transcript every turn; both providers now set a prompt-cache breakpoint on the system prompt, but only Anthropic also caches the growing tool-result prefix, and whether an OpenRouter-hosted free model honours `cache_control` at all depends on its upstream).
- **OpenRouter free-tier headroom**: 50 requests/day per account (1,000/day after ever buying $10 of credits once), 20 RPM — a single run's ~15-20 LLM calls can be a large fraction of a day's free allowance for one person. `OpenRouterProvider` retries 429s with backoff; there's no proactive "you're near your daily limit" signal yet beyond the 429 itself.
- **Nebius**: `extract_genes` runs on its regex fallback unless a `NEBIUS_API_KEY` is set (platform env var or BYOK via Settings).
- **Amass**: `drugcore`/`genecore`/`regulatorycore` record-to-citation mapping in `amass_tool.py` falls back to a generic name-like-field guess (their schemas weren't in the fetched OpenAPI spec) — `biomedcore`/`trialcore`/`patentcore` are mapped from confirmed schemas.
- **Grounding no longer hard-requires `AMASS_API_KEY`**: it has no free tier, so requiring it blocked every BYOK user with only a free LLM key. `backend/grounding/adapters.py`'s `PubMedPaperRepository`/`ClinicalTrialsRepository` are keyless equivalents of `AmassPaperRepository`/`AmassTrialRepository` (same `PaperRepository` port); `backend/grounding/runner.py::ground()` picks Amass when a key exists (BYOK or platform), else the keyless pair. `backend/agent/loop.py::_grounding_payload` now only requires an LLM key. `ground()` lives in `backend/grounding/runner.py`, not `scripts/run_grounding.py` — it has to be inside the importable `backend` package, since `scripts/` never ships to Vercel (`.github/workflows/deploy-frontend.yml` only stages `backend/`) and this was hit for real in production (`ModuleNotFoundError: No module named 'scripts'`) the first time grounding stopped short-circuiting on the (now-removed) `AMASS_API_KEY` check. `scripts/run_grounding.py` re-exports `ground` for its own CLI (`--premises`); its CLI-only concerns (`output()`/`archive()`/`live()`/`replay()`/`main()`) stay there.
- **Admin dashboard key rotation is unreliable on serverless**: `backend/agent/admin.py`'s file-based key-rotation overrides (`ADMIN_OVERRIDES_PATH`) and usage aggregation assume a persistent filesystem — true on the old Nebius VM, not true on Vercel's ephemeral-per-instance functions (a rotation can appear to succeed and then not be visible on the next invocation, which may be a fresh instance). Needs a real persistent store (a small free-tier KV/Postgres) to actually work there; not solved yet — see `docs/DEPLOY.md`'s Admin dashboard section. `ROTATABLE_KEYS` includes both `ANTHROPIC_API_KEY` and `OPENROUTER_API_KEY` so an operator can optionally set either as a platform fallback via the dashboard, even though neither is required or set by default (and rotation reliability is exactly the caveat above).
- **Knowledge trajectory is rendered client-side; cross-run accumulation still needs a persistent store**: `GET /api/trajectory`/`/api/trajectory/view` (`backend/kgviz/graph.py::snapshot()`) read `runs/knowledge.db`, which on Vercel never has anything in it — `SqliteKnowledgeBase` falls back to `:memory:` whenever the on-disk path isn't writable, and that DB dies with the request; `/api/trajectory/view` also hits the multi-segment routing bug below. So the app no longer fetches the trajectory at all: `frontend/src/lib/trajectory.ts` rebuilds the same graph (same node ids, edge kinds, virtual links and sorted BFS/DFS walk as `backend/kgviz/graph.py` — verified identical on the same fixture) from the run's own `grounding_step`/`grounding` events, and `components/KnowledgeTrajectory.tsx` is `backend/kgviz/viewer.html` ported to React (see the Frontend section). What that cannot show is exactly what only a persistent database holds — **other runs of the same question and each link's verdict history** — so the `/api/trajectory*` endpoints and the `kgviz` package stay for local use and for the day a real store (the same one the admin dashboard needs) is wired in; the natural shape is a connection factory behind `SqliteKnowledgeBase`/`kgviz` plus a "this run ↔ all runs of this question" toggle on the frontend view.
- **Parking lot — rate + re-evaluate**: let the scientist rate the AI evaluation (per-section accept/reject on the diff view, not a star rating — stars are useless as prompt input) and ask for another pass. The cheap version needs no backend work: fold the rejections into the existing `comment`, which `build_judge_prompt` already instructs the judge to treat as better-informed than its own read, and re-run from the original report. A true round 2 — critiquing the *revision* rather than the original — needs three changes: `EvaluateRequest` (`backend/server/app.py`) carrying the prior revision, `evaluate_hypothesis` taking a sections override instead of always splitting `run_result["report"]`, and prompt work to stop the judge simply re-affirming its own last revision. The frontend's evaluation list and the one-evaluation gate in `EvaluateBlock.tsx` are already shaped for more than one round.
